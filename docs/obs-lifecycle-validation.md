# OBS 生命周期修复与验证

## 已确认原因

2026-09-22 的源码中，`recorder.client()` 使用 `subprocess.Popen()` 启动专用 OBS 后丢弃句柄，没有记录本次应用实际启动的进程。`DesktopService.close_allowed()` 仅设置内部停止事件；主窗口退出与原生窗口循环返回都没有关闭 OBS 的步骤。Windows 子进程不会因为父进程正常退出而自动退出，因此存在完整的遗漏路径，不是托盘显示或回看窗口延迟退出的单一问题。

本轮只读进程核对发现安装目录中的一个 OBS 进程（PID 44544，2026-09-22 14:15:14 启动），其记录的父 PID 33072 已不存在。没有读取其连接凭证、录制状态或场次内容，也没有停止、重启或接管它。这一事实支持“已脱离退出父进程的 OBS”判断；无法仅凭该进程证明过去具体由哪个启动步骤创建。

关闭主窗口但保留回看窗口时，原设计会停止主窗口服务的监控，继续保留原生回看窗口；此前同样没有 OBS 清理路径。修复后在主窗口实际关闭时即执行录制引擎清理，回看窗口继续运行。最后一个原生窗口退出后还会等待同一清理结果，再释放应用实例锁。

## 修复边界

- 仅保留当前进程直接启动的 OBS 原始 `Popen` 句柄，按安装根目录隔离；连接到已有 OBS 不获得关闭权。不保存 PID 标记、不按进程名扫描接管，不关闭旧版遗留 OBS。
- 关闭前确认原始句柄仍存活、父 PID 是当前应用、可执行文件在该安装根目录内，并核实实际 WebSocket 对端的 TCP 连接属于这个子进程。身份在输出检查后再复核一次。
- 录制、推流、回放缓冲和虚拟摄像头都必须明确处于停止状态，且仍为 Experience 专用配置与场景。无法连接、缺失字段、权限受限或配置已变更时保留 OBS。
- 只向该子进程唯一匹配的 OBS 主窗口发送正常 `WM_CLOSE`，再次复核窗口所属 PID；等待正常退出，没有强杀、停止输出或重启兜底。正常关闭未确认则保留进程。
- 接受应用关闭后禁止后续启动/重连；清理与已接纳的设备操作同步，防止关闭时再次留下刚启动的 OBS。主窗口的关闭许可检查仍不阻塞原生 UI。

`psutil==7.2.2` 已在原有锁定依赖及 Windows 运行时中，本轮没有新增依赖。

## 仍有整理任务时的二次确认

保留现有保守门槛：录制、保存、整理及后台排队任务未完成时，关闭主窗口不会立即被接受。确认后先等待工作安全完成，再关闭主窗口并清理 OBS；取消则保留主窗口、任务和 OBS。无法确认录制状态时仍拒绝安全退出，不能用关闭 OBS 代替完成录制保存。

当后台场次正在整理或排队时，当前原生确认对话框标题为 `关闭记录器`，传给 `create_confirmation_dialog` 的准确正文为：

> 还有场次正在整理或排队，完成后可以安全关闭。
>
> 结束当前录制，并等待保存和整理完成后关闭此窗口？已打开的回看窗口会继续保留。

新增服务与窗口管理器联动回归分别验证确认和取消：任务未结束前不得调用 OBS 清理，确认后必须等队列清空；取消不设置关闭状态，也不销毁窗口或请求退出 OBS。这是合成联动检查，未对用户当前应用弹出确认框。

## 验证记录

新增合成回归覆盖进程归属、PID 复用、不同安装根、确切 TCP 对端、活动或未知输出、连接失败、手工切换配置、正常关闭未确认、关闭后的延迟连接，以及主窗口关闭后回看窗口继续保留。进程和原生控制调用均使用合成替身，不操作现有用户 OBS。

定向测试首次运行：110 项通过。全量首次运行发现既有 shell 测试替身没有 `closed` 事件，本轮补齐该事件并加入原生循环返回时必须完成清理的断言。加入整理中二次确认的确认/取消联动回归后，最终使用原有 Windows 私有运行时、当前 worktree 优先导入，完整 Python 测试 **185 项通过**；负责文件 `git diff --check` 通过。

另外实测了一份位于 ignored `work/obs-lifecycle-smoke/run-20260922-145743` 的独立 OBS 安装目录。其配置、随机端口、凭证、空场景都为本次验证新建，未使用用户配置。报告 `report.json` 记录 **7 项通过**：原始子进程句柄仍存活、确切 TCP 对端属于该子进程、没有采集输入、全部输出未活动、正常关闭获确认、子进程实际退出、验证前已有 OBS 身份不变。测试 OBS PID 39940 已退出；原有用户 OBS PID 44544 保留。此结果验证了当前打包 OBS 在 `--minimize-to-tray` 启动状态下收到正常 `WM_CLOSE` 会真正退出，而非仅隐藏窗口。

首次原生验证发现未启用的回放缓冲没有可查询状态对象，实际返回 604。修复改为读取完整输出清单，覆盖已实例化的回放缓冲、虚拟摄像头及插件输出；录制/推流仍另行明确检查。此前失败样本保留于 `run-20260922-145410/report.json`，其专用测试子进程最终仅通过正常 `WM_CLOSE` 退出，追加清理记录位于 `fixture-cleanup.json`。同时发现持有 WebSocket 等待 OBS 停服会延迟进程退出，因此关闭请求成功后先断开本次验证连接，再等待进程退出；已有回归断言保证这一顺序。没有强杀任何测试或用户进程。

## 使用限制

该修复负责新版应用本次启动的 OBS。安装修复前已经遗留或手工启动的 OBS 不具备可信归属，仍需用户自行处理，不能为清理后台进程而猜测接管。正常关闭请求未获确认或无法证明输出已停时，也可能有意保留 OBS。

## 2026-09-23：退出后仍占用安装目录

在 `D:\Think Aloud 0.6.0` 观察到 PID 57776 的 `obs64.exe` 仍从该目录运行，原父进程 PID 53552 已不存在。OBS 日志显示 14:14:50 开始关闭、14:14:51 WebSocket 已停止并释放场景，但进程仍有一个线程和大量句柄，任务列表报告“未响应”。此时无法再通过 WebSocket 查询输出。经核对可执行文件路径、启动时间与已完成的 OBS 关闭日志后，仅对该确切进程发出终止请求，并再次确认进程消失；没有删除安装文件或碰触资料库。

新版在启动专用 OBS 时，将进程 PID、创建时间、父 PID、可执行文件和安装根写入 `state/owned-obs.json`，不写连接凭证。应用重启后，仅在这些身份全部匹配时重新认领原子进程；未知进程、PID 复用、不同安装根或不匹配的 WebSocket 对端仍不得关闭。关闭前仍需确认录制、推流及全部输出已停，且专用配置与场景未变。正常 `WM_CLOSE` 等待 8 秒超时后，再次核对进程身份，才对已确认空闲的该进程执行终止并等待退出；身份或状态无法确认时保留进程。

本地修复以校验过的 preview.5 软件包为基底，修复中断覆盖造成的 7 个内容不符文件和 1 个缺失的默认术语文件，再叠加上述 OBS 修复，共更换 12 个托管文件。安装结果标记为 `0.6.0-preview.5+local.1`，仅用于本机，不是 GitHub Release。事务与完整备份位于 `D:\Think Aloud backups\20260923-152540-obs-exit-repair`，其中保留了恢复入口。安装后清单中 7,335 个文件全部匹配，35 个被检查的配置、密钥、OBS 配置及个人词库文件与备份一致，打包程序的 `--self-check` 通过。

源码完整 Python 回归 377 项通过、1 项跳过。实际从修复后的安装路径启动记录器，观察到新 OBS PID 65012；未开启录制或推流，随后正常关闭主窗口，记录器返回 0，OBS 进程也退出。原始验证记录保留在备份目录的 `transaction/installed-self-check.json` 与 `native-smoke.json`。此检查覆盖本机单次启动、就绪及正常退出；退出卡死时的终止分支由合成测试和上述真实卡死进程处置分别提供证据，尚未在第二次可控卡死的 OBS 上复现。
