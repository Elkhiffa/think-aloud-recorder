# 体验洞察流程调研：专业做法 × 现有 agent 流程（2026-10-20）

**目标**：让 agent 产出的跨场次报告，能交给专业 UX 设计师接着分析、找设计机会点。
**本文做了三件事**：
1. 调研专业人士怎么做这部分工作、用什么工具；
2. 盘点现在的单场整理、跨场次归类和报告流程；

本轮不改 skill、代码和资料库。

## 结论

1. **你的判断有依据，但更准确的说法是“三步只做了中间一步”。** 专业做法是三步：
   - 先搭框架：研究目标，以及设计意图，也就是玩家在这里应该理解、做到、感受到什么；
   - 证据从下往上填进框架；
   - 最后按论点收口，收成少数几条有观点的主题。

   现在的流程只做了中间这一步，而且做得很全。顶层洞察虽然由你定义，但既没有设计意图，也没有本次要回答的问题，最后也没有收口。（附录 A §1.3，附录 B §1）

2. **差距最大的有三处。**
   - **没有“设计意图”这一层。** 判断“这是不是问题”时，不对照设计想让玩家怎样。所以分不清有意的摩擦、好的“被岔开”和真正的问题。例子：三条“四十多分钟后才想起原来目标”的时间线，现有议题都记成问题：0930 和 0921 在 TA-04.5，1005·0222 在候选 N-010.1。你判断它们是正例。
   - **一棵议题树兼了两份工作。** 它既是证据库的标签，又是报告的论点结构。结果有三个：
     - 顶层多是话题桶：“难懂的术语和图标”“外观相关的断点”；
     - 底层碎片化：278 个叶子议题里，111 个只有不超过 2 条证据；
     - 报告“按证据条数从多到少”排了 19 节，读起来像清单。
   - **只到现象，没到症结。** 议题不写“游戏里的原因”。合并看描述像不像，而不是看能不能用同一个修复解决。演讲里的几条症结都是你补的，例如“机制有主线、传达没有主线”和“快捷跳转方便了玩家，也让路径曝光不足”。

3. **有几处走在专业工具前面，要保留。**
   - 每句话都能回到录像的那一秒：45 场报告 1495 处引用，全部可解析。
   - “说出口的时间”和“所指的时刻”分开记。
   - 证据分支持和反例。
   - 界面目录和系统、玩法标签是独立的维度。
   - 有“有问题”反馈通道。

   见第四节。

4. **推荐方向：把“证据库”和“洞察报告”拆成两个产物。**
   - 证据库继续从下往上长，加上卫生规则：定义、纳入例、排除例，合并按“同一修复”判断。
   - 报告每次按一份“分析简报”从上往下写，依次是：
     1. 本次读者和要回答的问题；
     2. 设计意图和它的来源；
     3. 按症结合并问题；
     4. 每条写原因、影响、严重度；
     5. 论点开头，少而强；
     6. 解法交给设计师，写成机会点。

   你演讲用的“不对劲 → 定位 → 症结 → 改法”，正好就是这一套的专业版本（第五节）。

5. **单人自玩要换定位。** 这批材料更接近“专家评审 + 46 场纵向记录”，不是玩家测试。所以有两处要改：
   - 跨场次重复出现，说明的是同一个人反复被困扰，也就是“持续性”，不代表“玩家普遍遇到”。
   - 严重度用固定问题判断：核心体验吗？难克服吗？反复出现吗？不按条数判断。（附录 A §4.4，附录 B §2.2、§6）

6. **Claude 和 Codex 的倾向正好对应拆开后的两个产物。**
   - Codex 的报告更接近专业报告的形状：5 个横向主题、边界说明、BUG 复测表。
   - Claude 的产出更像证据库：建树、挂证据、数字都能对上。
   - 这个分工要先用同一份新说明再测一次，才能定。

## 一、专业人士怎么做

### 1.1 流程：先搭框架，再填证据，最后收口

| 步骤 | 专业做法 | 主要来源 |
|---|---|---|
| ① 定框架 | 研究目标由设计、制作一起定。每个目标问清设计意图：玩家在这里应该理解什么、做到什么、感受什么。意图不清，同一个“死了 3 次”无法判断是好是坏 | Bromley 2021《Defining research objectives》《Designing a games user research study》（附录 B §1.1） |
| ② 观察 | 记录“偏离意图”的地方，**同时记录按意图运作的地方**，免得团队把它改坏 | Bromley 2021《Analysing…》（已核对原页） |
| ③ 分组、提炼 | 先按研究目标、关卡或机制分组，再在组内提炼独立问题。**判断是不是同一个问题，看团队是否需要分别修复**：同一个原因、一个修复能解决，就算同一个问题，哪怕发生在不同地方 | 同上（jetpack 例） |
| ④ 写问题 | 每条写成：陈述 + 原因 + 影响。**原因写成游戏的属性**，例如物件、布局、之前的流程。写成“玩家不理解”说明还要往下挖；“缺少教程”这种把方案写成原因的，不合格 | 同上 |
| ⑤ 定严重度 | 用固定的三问，不按人数：是不是核心体验？是不是难以克服？同一个人会不会反复遇到？在定性研究里按受影响人数排序有风险 | Bromley 2023《How to prioritise…》（已核对原页）；Nielsen 1994 |
| ⑥ 写报告 | 开头一句论点级洞察，加一页摘要，然后是分组问题、详情、下一步。按洞察类别分组，不按功能分组。发现太多会稀释影响力 | Bromley 2022 引 EA 的 Jess Tompkins（已核对原页）；Mirza-Babaei 2018 |
| ⑦ 交付 | 现场讲解，加上行动工作坊。默认由设计师出方案，研究员把问题写成“我们如何才能……”式的挑战 | Bromley 2021《Debriefing a study》、2025《Stop Being Ignored》 |

### 1.2 几条判断标准

- **主题要有观点，不能是话题桶。** “X 的障碍”“Y 的体验”这类名字只是在概括一个话题，说明分析停在了描述层。（Braun & Clarke 主题分析 FAQ；NN/g Rosala 2022 把“只描述、不分析”列为陷阱。附录 A §2）
- **自下而上有它的用处，不能删。** 亲和图刻意不预设类目，是为了防止研究者只看见自己预期的东西。所以要做的是加一层框架、再加一道收口，而不是把从下往上换成从上往下。（NN/g 2024 亲和图；附录 A §0）
- **少量样本的计数。** 只写原始数，不换算成百分比；频次和严重度分两栏写；亲和图会因为“很多人记了同一件事”而放大某个问题的重要性。（Moran 2021；Sauro 2013；GOV.UK Fu 2019）
- **单个评估者有局限。** 一个人给的严重度不可靠，取 3 人平均才够。两名评估者找到的问题，重叠率中位数只有约 27%。设计者评自己熟悉的设计，容易犯“错误共识”和“知识的诅咒”。（Nielsen 1994；Sauro 2018；Budiu 2017；Hodent。附录 A §4、附录 B §3.2）
- **只看口述不够。** 只看转写稿，人和 AI 都分析不了可用性测试（NN/g 2023）。玩家自己说的原因也不等于诊断：玩家说“太难”，真正的原因可能是引导不清（PlaytestCloud Kulik 2026）。

### 1.3 工具怎么做

各家工具都把三层分开存放：
- 证据：片段、高亮；
- 标签：由人维护的标签体系；
- 洞察文档：另外写成的文档，引用证据。

层级是人去建、去合并、去锁定的，不是聚类自然长出来的。（附录 C §1）

| 工具 | 和本题相关的做法 |
|---|---|
| Dovetail | 2026 年的标签体系指南：2–3 层，顶层 4–8 类，起步 20–40 个标签；每个标签都有定义、纳入例、排除例；**从单个研究自下而上搭是最常见的错误**（已核对原页）。标签表达主题，产品区域、方法、日期这些结构信息用字段记 |
| Condens | 全局标签可以锁定；项目标签用来发现新主题，复现之后才升为全局标签 |
| Looppanel | 先上传提纲，AI 按问题归档笔记；先审阅 AI 建议的标签表，再批量打标签 |
| Lookback | 先定义目标，AI 按目标找时刻；“AI 不决定什么重要” |
| PlaytestCloud（游戏） | 先配置：从 13 个类目里选最多 6 个，再写研究问题和游戏描述，AI 照这个出初步发现；“为什么”和建议留给人 |
| NN/g 的评测（2023→2024→2026 立场一致） | AI 编码只能当初稿；工具拿不到研究目标，就排不出重要性，曾把琐碎发现排第一 |

学术上效果最好的做法有这样几个共同点：
- 每个主题带明确的纳入判据，能用判据把全部数据重新打分；
- 子主题在父主题下生成，并引用证据；
- 每次归类都写理由；
- 引文逐字核对原文；
- 对没被任何主题覆盖的材料，再单独补一轮。

已知的弱点有四个：
- 解释层的主题做不好；
- 类目外、间接表达的内容会漏；
- 重跑结果会变；
- AI 起草的框架会锚定人的思路。

## 二、现状：现在的流程实际怎么走

```
录制 → 转写（只转纯麦克风轨）+ 情景轨道（每 5 秒画面文字）+ 按键记录
  │
  ▼
① 单场整理（think-aloud-judgments；生产上交 Codex）
   产出：判断实例（类型、说出口时间、所指时刻、界面、跳转路径、陈述、证据、可信度）
         + 游戏内活动
   不打议题标签（只有记录者明说的 BUG 例外）
  │
  ▼
② 跨场次（think-aloud-insight；主线程临场拆成 分组归类 × 9 → 汇总写入 → 标签 → 报告）
   分组：逐条实例往现有议题树上挂；挂不上的写一句“模式”
   汇总：各组的模式聚成新子议题（≥2 条证据）、挂支持或反例、BUG 分组
   报告：总体判断（3–5 个问题、关系、优先级）→ 每个洞察一节 → 待决 → BUG
  │
  ▼
③ 洞察窗口：报告 + 证据树 + 界面库；“有问题”反馈 → ④ 下一轮 agent 优先采纳
```

在 46 场镜像库上的实际形状：

| 项目 | 数值 |
|---|---|
| 判断实例 | 2913 条，其中 1956 条挂了议题 |
| 议题 | 328 个：顶层 19、第二层 184、第三层 125 |
| 叶子议题 | 278 个，其中 111 个只有不超过 2 条证据 |
| 议题上记的字段 | 只有编号、上级、状态、标题、说明；没有严重度、影响、设计意图、原因 |
| 45 场报告 | 约 11.9 万字，1495 处引用；“顺序按证据条数从多到少” |

顶层 19 个洞察混了四个维度：
- 问题类型：术语、预期、注意力、执行摩擦、入口、反馈；
- 输入设备：手柄；
- 系统或内容：外观、探索、战斗、新玩法、剧情；
- 动机：驱动、心理成本、资源流转、重复成本。

## 四、要保留的（先查清它们为什么存在）

| 现有设计 | 为什么存在（出处） | 和专业做法的关系 |
|---|---|---|
| 单场不打议题标签，跨场次再归类 | 单场整理要“脱离本场被独立读懂”，避免一边整理一边被现有议题带偏（judgments skill 开头；HANDOFF §1） | 和“先描述、后解释”一致，保留 |
| 陈述不加原话里没有的判断，推断要写明是推断 | 防止 agent 编造判断；对比时，两位评审都查出过加解读的问题（comparison §2.2） | 和逐字核对、事实层不含推断一致。注意：它**不禁止**写原因，只要求原因标成推断。所以写症结和这条规则不冲突 |
| 子议题至少 2 条证据才建、默认 confirmed | 降低你逐条确认的负担（HANDOFF §1，10-14 决定） | 门槛本身没问题；碎片化来自“按描述聚类”。要改的是合并标准，不是门槛 |
| 界面目录、系统和玩法标签与议题树分开 | 界面库筛选需求（HANDOFF §1，10-14） | 正是 Dovetail 说的“结构信息用字段，标签表达主题”，保留，以后报告的骨架可以直接用它 |
| 每个引用都能回到录像那一秒 | 洞察窗口的核心交互 | 超过 NN/g 对现有工具的评价（他们发现引用常常不带场次和时间戳），保留 |

## 五、核心方向：怎么从上往下组织

你演讲的四步和专业做法一一对应：

| 你的讲法 | 专业的叫法 | 产出 |
|---|---|---|
| 不对劲 | 偏离设计意图的观察（Bromley） | 原话、片段，也就是证据库里的实例 |
| 定位 | 原因写成游戏属性 | 问题陈述 + 原因 |
| 症结 | 同一修复合并、中心论点（Braun & Clarke 的“中心组织概念”） | 论点级主题 + 图解 |
| 改法 | 机会点、“我们如何才能……”，由设计师出方案 | 机会点清单 |

三种真正不同的做法：

| | A. 框架先行：先编好标签表再归类 | B. 拆成两个产物：证据库 + 按简报写报告 | C. 假设先行：你先写论点，agent 核证据 |
|---|---|---|---|
| 怎么做 | 你和 agent 先定 4–8 个顶层主题，每个写定义、纳入例和排除例；每轮按这张表归类，归不进去的单独补一轮，提出新主题交你批准 | 证据库照现在从下往上长，加卫生规则。每份报告先写一份简报：给谁看、回答什么、设计意图从哪来、按什么分组。agent 按简报做症结合并、严重度、论点开头、机会点 | 你写出要讲的论点和猜测的症结，agent 在 46 场里找支持、反例和缺口，删掉证据撑不住的 |
| 明显胜出的场景 | 同一套问题要反复回答、多轮之间要能比较，比如每个版本都要追踪同几个系统 | 读者各不相同：战斗组、养成组要不同的切法；材料还在增加；又要留住意外发现 | 你已经有很强的判断，需要快速拿证据或挑战它，比如今天的演讲、设计评审前 |
| 风险 | 漏掉框架外的新现象；AI 起草的框架会锚定思路 | 两个产物要保持同步；症结和严重度更依赖推理质量和回看录像 | 确认偏误；很依赖你的时间 |
| 对现有的改动量 | 大：议题树要重建 | 中：证据库基本不动，新增“简报 + 综合”一步，报告格式重写 | 小：新增一种任务形态 |

**推荐 B 为主，A 和 C 作为 B 里的两个可选输入。**

理由：
- 你的终局读者是专业 UX 设计师，而组内按系统分工，同一批证据需要不同的切法，固定一张表不够用。
- 现有的证据库，包括可追溯性和标签，是这个项目最强的部分，B 不推倒它。
- 简报里可以选一套现成框架，比如按系统、按体验阶段、按 Hodent 维度，这就是 A。
- 简报里也可以直接写上你的假设，这就是 C。

B 里的“综合”一步具体包括：
1. **简报**，你确认后开工：读者；要回答的问题；设计意图和它的来源（你的判断、游戏内的攻略和提示原文、项目设计文档）；分组骨架；本次不管什么。
2. **取证**：按骨架从证据库取实例，不重新整理场次。
3. **定位和症结**：
   - 原因写成游戏属性，“玩家不理解”算没挖完；
   - 按“同一修复”合并；
   - 涉及机制的判断，回看录像、读游戏内攻略原文核实；
   - 推断写明是推断。
4. **定级**：三问，核心体验？难克服（要查攻略、靠队友、长时间卡住）？跨场次反复出现？频次只写原始数，标明是“持续性”。
5. **报告**：
   - 论点开头，加一页摘要；
   - 每组写不对劲、定位、症结、机会点；
   - 单列“按意图运作的”；
   - 主体只放现在要知道的，其余留在证据库；
   - 首页写明适用边界。
6. **检查点**：症结的命名、主题和优先级交你拍板；所有 agent 产出标明“AI 初稿”。
