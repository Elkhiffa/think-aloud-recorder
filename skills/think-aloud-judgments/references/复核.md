# 复核：在别的模型整理的结果上补漏

任务说明要你复核一场已有整理结果的场次时，按这份做。判断标准全部沿用 SKILL.md 和案例。

## 为什么要复核

第一轮整理记下来的条目大多可用，弱点是漏记，以及把受阻或理解困难记成观察。这些漏掉的问题读者看不见，也就没有机会批注。所以复核的主要任务是找回漏掉的问题，不是把每条重写一遍。整场重做的费用接近一轮完整整理，复核省下的正是这部分，把力气放在差异上。

## 流程

1. **领取**：用 `reprocess`，令牌和工作文件的规矩同 SKILL.md。

2. **先自己过一遍，再看第一轮。** 先看别人的结果，容易只在它的框架里挑错，漏掉的还是漏掉。所以先读全场原话、情景文字和操作摘要，按 SKILL.md 的标准列出你认为该记的问题和 bug，写进工作目录的 `own-list.md`。这一步只求覆盖，不用写完整陈述；不看画面定不了所指的，先标“待查”，到第 4 步再截图。

3. **再读第一轮结果**（场次的 `experience-events.json`），逐类对照：
   - **你列了、它没记的**：最重要的一类。
   - **没被任何实例引用的原话**：逐句看一遍，表达了困惑、受阻或评价的，是不是漏了。
   - **记成观察的**：按“看过程，不看结局”重新判断。写着“没有足够依据”的，先看过程里有没有受阻或理解困难。
   - **类型和 bug**：明显不对的才改。两个缺陷都成立、改法也不同时，填 `secondary_defect` 或拆成两条，不要二选一。
   - **陈述**：读者读不出“为什么算问题”的，补上这一环。

4. **只为差异回素材取证。** 第一轮已经核实过的事实不用重看，新增和改动的条目要照 SKILL.md 取证。截图时留意画面本身的显示错误（截断、超框、重叠）；数字和实际对不上时，先查它是不是别的口径（单价、单位、另一种货币）。是别的口径，就不算 bug；画面没有说明口径的，仍是设计问题，按预期传达有误记，写清画面上的数字和实际的差别。确实错了、记录者又没提的，记 `bug: suspected`，写明要 QA 核实什么。`said` 必填，挂当时最近的一句原话；`evidence_source` 填 `behavior`，并在陈述里写明这是从画面看到的、记录者没有提。

5. **改结果**：在第一轮结果上改，放到工作目录，去掉上一轮的 `receipt`。
   - 没问题的条目保留原文和编号，不为措辞或个人偏好改写：读者已经能读懂的条目，改写只会多花费用，还可能引入新错。
   - 新增条目用新编号，接在最大编号之后。
   - 只有事实错了或不该记时才删除，并写明依据。
   - 类型两可时保留第一轮。过程里有受阻或理解困难却记成观察的，不算两可，按“看过程，不看结局”升级。

6. **校验、提交、命名**：同 SKILL.md 的第 7、8 步；提交后重新命名，因为命名绑定这一次提交。

## 过程记录

在工作目录写 `review.md`，它代替 SKILL.md 要求的 `process.md`，如实写：
- 第一轮多少条，复核后多少条；
- 每处改动：哪一条，新增、升级、改类型、补陈述还是删除，依据是什么（原话、画面时刻）；
- `own-list.md` 里哪些第一轮已经覆盖；
- 看了多少帧，新增了多少条实例。
