# 跨场次分析与洞察报告

记录者是专业 UX 设计师。各场的判断实例已经由单场次整理完成，每条都带有“说出口的时间”“所指时刻”“界面”“陈述”和证据。你的任务是在资料库层面把它们组织成能直接用于体验设计决策的分析：

```
报告（总体判断 → 主题）  →  议题 → 子议题  →  论断（判断实例，支持或反例）  →  回看时刻
```

洞察界面左栏显示你写的报告，右栏按议题和子议题列出证据；读者点报告里的引用，右栏会定位到那条证据，再从证据打开回看。所以**报告里的每个判断都要能点到证据**，子议题里的每条证据都要真的支持（或反驳）它。

命令都在仓库根目录执行：`runtime/python.exe -B -X utf8 agent_cli.py <命令>`，输出是 JSON。

## 输入

- `issues-list VAULT`：议题表。`TA-` 由用户定义；`N-` 是候选；`BUG` 是固定议题；带 `.n` 的是子议题。
- `instances-query VAULT [--issue ID] [--screen ID] [--kind K] [--session S]`：已完成场次的全部实例。查父议题会带出子议题的证据；每条的 `issue_links` 写明议题、理由和角色（`support` / `counter`）。
- 界面目录：`VAULT/game-assets/<游戏>/catalog.json`。实例的 `screen` 是目录编号或别名时，`catalog_screen` 给出正式编号；`screen_proposed` 为真且 `catalog_screen` 为空的，是尚未确认的提议界面。
- `bug-hits VAULT`：记录者原话里提到 bug 的每一处，`state` 为 `linked`（已挂 BUG）、`instance`（成了实例但没挂）、`raw`（没成为实例）。
- 任务说明里给出的上一轮分析材料（如各议题的补充和反例），以及用户对归类的修正。用户修正优先于任何旧材料。

只读实例通常够用。陈述读不懂时，宁可不挂，也不要猜；确实需要原话时，在过程记录里写明回读了哪一场哪一条、为什么。

## 步骤

1. **通读**：导出全部实例，按议题读一遍现有对应，先读用户修正。
2. **子议题**：把每个议题下反复出现的具体模式写成子议题。
   - `issues-add VAULT --parent TA-04 --title "…"` 自动编号为 `TA-04.1`、`TA-04.2`……；再用 `issues-update VAULT TA-04.1 --description "…"` 写**成立的理由**：这个模式是什么、为什么是设计问题、证据覆盖几场几条、有什么边界或反例。
   - 子议题的标题写成一个可检验的设计判断或设计问题，不写成分类名（写“清完提示后玩家忘了原本目标”，不写“目标问题”）。
   - 至少 2 条证据才建子议题；只有 1 条的留在父议题下，不细分。
   - 子议题只有一级。
3. **挂证据**：`issues-link VAULT --file links.json`，每行 `{issue, session_id, instance_id, reason, role}`。
   - 挂到最具体的子议题上，不要同时再挂父议题。原来挂在父议题下的证据归入子议题后，用 `issues-unlink VAULT <父议题> --session S --instance I` 移除父议题那条；归不进任何子议题的留在父议题下。
   - `role: counter` 用于反例：同一设计在别处起了作用、玩家欢迎相反的做法、或边界情况。反例的理由要写清它反驳的是哪一点。
   - `reason` 写一句这条证据说明了什么，不重复陈述原文。
   - 整批写入前先自查：议题存在、实例存在、没有重复。
4. **BUG 分组**：读 `bug-hits`。`linked` 和 `instance` 状态的实例，按“是不是同一个 bug”分组，建 `BUG` 的子议题（如“手柄焦点被独占”），并把实例挂进去。闲聊或别人说的不挂。`raw` 状态没有实例可挂，在报告的 BUG 段落里如实列出时间和原话。
5. **写报告**：写到 `VAULT/洞察/<日期>-<名称>.md`，格式见下。
6. **校验**：`insight-validate VAULT <报告文件名>`，`unresolved` 为空才算完成；再用 `issues-list` 核对每个子议题的对应数。
7. **过程记录**：在任务说明指定的位置写过程记录：做了什么、回读了什么、哪些实例没挂及原因、给用户的待决问题。

## 报告格式

- 开头是**总体判断**：用几段话说清这批材料最重要的 3–5 个体验问题、它们之间的关系，以及最值得优先处理的是什么、为什么。
- 然后**按主题展开**。主题可以跨议题，例如“目标明确时，摩擦来自界面还是机制”；每个主题说明涉及哪些议题和子议题、核心论点、证据、反例、设计含义和待验证的问题。
- **最后一节写 BUG**：分组列出，每组写现象、出现的场次和时刻，以及未整理的原话。
- 引用写法：
  - 实例：`[0924 i72](i:<session_id>/i72#TA-04.5)`。方括号里是短标签：场次 id 的月日（`20260924-…` 写 `0924`）加实例号；同一天有几场时，加开始时分区分，如 `0924·1531 i72`。`#` 后写这条证据在右栏所属的议题或子议题；不属于任何议题时省略 `#…`。
  - 议题：`[TA-04.5](issue:TA-04.5)`。
- **有理有据**：
  - 每个论断后面紧跟引用，一个论断引用 1–3 条最有代表性的证据，不堆砌；
  - 明说、画面或操作观察、你的推断要分开写，推断写成推断；
  - 记录者的原话加引号；数字（场次数、条数）以查询结果为准；
  - 不加原话和实例里没有的判断，不用泛化的 UX 术语替换记录者的说法。
- 可以用标题、段落、列表、加粗和简单表格。不要用图片或 HTML。

## 不做

- 不改写任何场次的 `experience-events.json`，不重新整理场次。
- 不新建、不改名 `TA-` 议题；不合并议题。认为该合并或拆分时，写进过程记录交给用户。
- 不改界面目录。界面名称的问题写进过程记录。
