# 跨场次分析与洞察报告

记录者是专业 UX 设计师。各场的判断实例已经由单场次整理完成，每条都带有“说出口的时间”“所指时刻”“界面”“陈述”和证据。你的任务是在资料库层面把它们组织成能直接用于体验设计决策的分析：

```
报告（总体判断 → 主题）  →  洞察 → 议题 → 子议题  →  论断（判断实例，支持或反例）  →  回看时刻
```

洞察界面左栏显示你写的报告，右栏按洞察、议题、子议题列出证据；读者点报告里的引用，右栏会定位到那条证据，再从证据打开回看。所以**报告里的每个判断都要能点到证据**，子议题里的每条证据都要真的支持（或反驳）它。

命令都在仓库根目录执行：`runtime/python.exe -B -X utf8 agent_cli.py <命令>`，输出是 JSON。

## 输入

- `issues-list VAULT`：议题表，最多三层：洞察（顶层）→ 议题 → 子议题，`parent` 指向上一级，中间的议题层按需设置。`TA-` 由用户定义；`N-` 是候选；`BUG` 是固定洞察。编号只是工作代号，挪动层级时不变，所以编号前缀不一定是现在的上级。
- `instances-query VAULT [--issue ID] [--screen ID] [--kind K] [--session S]`：已完成场次的全部实例。查上级会带出它下面所有层级的证据；每条的 `issue_links` 写明议题、理由和角色（`support` / `counter`）。
- 界面目录：`VAULT/game-assets/<游戏>/catalog.json`。实例的 `screen` 是目录编号或别名时，`catalog_screen` 给出正式编号；`screen_proposed` 为真且 `catalog_screen` 为空的，是尚未确认的提议界面。
- `bug-hits VAULT`：记录者原话里提到 bug 的每一处，`state` 为 `linked`（已挂 BUG）、`instance`（成了实例但没挂）、`raw`（没成为实例）。
- `feedback-list VAULT --open`：用户在洞察窗口里对议题或证据标记“有问题”时留下的反馈，每条写明指向哪个议题或哪条证据、该怎么调。
- 任务说明里给出的上一轮分析材料（如各议题的补充和反例），以及用户对归类的修正。用户修正优先于任何旧材料。

只读实例通常够用。陈述读不懂时，宁可不挂，也不要猜；确实需要原话时，在过程记录里写明回读了哪一场哪一条、为什么。

## 步骤

1. **通读**：先读未处理的用户反馈和用户修正，再导出全部实例，按议题读一遍现有对应。反馈按用户修正对待：能直接改的（挪位置、改说明、改挂、移除对应）就改；涉及洞察新建、改名、合并的，写进过程记录交给用户。每处理完一条，用 `feedback-resolve VAULT <反馈编号> --note "…"` 写明改了什么。
2. **议题和子议题**：把每个洞察下反复出现的具体模式写成子议题；同一洞察下子议题多、能分成几组时，用中间一层议题把相近的子议题归在一起。
   - `issues-add VAULT --parent TA-04 --title "…" --status confirmed` 自动编号为 `TA-04.1`、`TA-04.2`……；`issues-move VAULT <编号> --parent <新上级>` 把已有议题挪到新的上级，编号和证据都跟着走。再用 `issues-update VAULT TA-04.1 --description "…"` 写**成立的理由**：这个模式是什么、为什么是设计问题、证据覆盖几场几条、有什么边界或反例。
   - 标题写法分三层：洞察是几个字点名一类问题（如“目标明确时，仍有执行摩擦”）；议题是这一类下的一个问题面；子议题写成一个可检验的设计判断，不写成分类名（写“清完提示后玩家忘了原本目标”，不写“目标问题”）。
   - 至少 2 条证据才建子议题；只有 1 条的留在上级下，不细分。BUG 例外：按“是不是同一个 bug”分组，1 条也单独成组，BUG 保持两层。
   - 最多三层。议题和子议题直接新建为 confirmed，默认接受，用户发现问题会留反馈；洞察的新建、改名、合并只写建议，交给用户。
3. **挂证据**：`issues-link VAULT --file links.json`，每行 `{issue, session_id, instance_id, reason, role}`。
   - 证据是标签式的：一条证据可以同时挂给多个议题（例如同一段话既是心理成本、又是驱动缺失），只要每一处都确实支持或反驳它；议题本身是树，每个议题只有一个上级。
   - 挂到最具体的一层上，不要同时再挂它的上级。原来挂在上级的证据归入下级后，用 `issues-unlink VAULT <上级> --session S --instance I` 移除上级那条；归不进任何下级的留在上级。
   - `role: counter` 用于反例：同一设计在别处起了作用、玩家欢迎相反的做法、或边界情况。反例的理由要写清它反驳的是哪一点。
   - `reason` 写一句这条证据说明了什么，不重复陈述原文。
   - 整批写入前先自查：议题存在、实例存在、没有重复。
4. **BUG 分组**：读 `bug-hits`（关键词含 bug、Cocos、引擎、报错、闪退，以及跑测常用的重叠、裁切、适配、歪了、偏了、偶现、不显示、没显示、超框、看不全、悬空、标错；这些词只是机械匹配的候选，也可能是在评价设计，逐条判断）。`linked` 和 `instance` 状态的实例，按“是不是同一个 bug”分组，建 `BUG` 的子议题（如“手柄焦点被独占”），并把实例挂进去。闲聊或别人说的不挂。`raw` 状态没有实例可挂，在报告的 BUG 段落里如实列出时间和原话。
   - 记录者没说是 bug、但描述的是功能或显示异常的实例（画面多出遮挡、按键失灵、光标或状态残留、操作时灵时不灵），同样建为 **BUG 的子议题**，标题前加“疑似：”，说明里写清为什么怀疑是缺陷、可能其实是设计或环境的理由；用户不认可时会留反馈。这些实例原来的设计议题对应保持不变。
5. **写报告**：写到 `VAULT/洞察/<日期>-<名称>.md`，格式见下。
6. **校验**：`insight-validate VAULT <报告文件名>`，`unresolved` 为空才算完成；再用 `issues-list` 核对每个子议题的对应数。
6a. **系统和玩法标签**（任务说明要求时做）：`tags-report VAULT` 读出现有标签、各标签条数、没有标签的证据和没打标签的活动；改好 `tags.json` 后用 `tags-write VAULT --file <文件>` 整份写入（先校验再写）。
   - 标签按维度分组，维度顺序固定为“跨系统”“系统”“活动 / 玩法”（跨系统放跨系统的总体评价，如红点、目标）；名字用玩家认得的叫法；一条证据可以有多个标签，和它的跳转路径无关。
   - 每个标签给关键词：证据所在界面的正式编号（目录里没有时用原始写法）出现关键词就自动命中。跳转路径和旧写法不参与匹配：“从哪儿来”由活动标签表达，系统标签只表示证据所在的界面。
   - 逐个活动读标题和摘要，判断这个活动是从哪个系统、玩法进入的，写进 `activities`；活动里的每条证据都继承，没有界面名的战斗、HUD 和自带名字的结算界面靠它找到来源。判断不了就不打，写进过程记录。
   - 关键词误命中或漏掉的，用 `assignments` 逐条增减。封面由用户在洞察窗口设置，不要改动 `cover`。
7. **过程记录**：在任务说明指定的位置写过程记录：做了什么、回读了什么、哪些实例没挂及原因、给用户的待决问题。覆盖范围变了的洞察，给出建议标题，交用户决定。

## 报告格式

- 开头是**总体判断**：用几段话说清这批材料最重要的 3–5 个体验问题、它们之间的关系，以及最值得优先处理的是什么、为什么。
- 主题标题用几个字直接点名问题本身，如“目标丢失”“目标明确后，仍有摩擦”“操作前的功能预期”“难懂的术语”；不用设问句、引语或“A 还是 B”式的标题。
- 然后**按主题展开**。主题可以跨议题，例如“目标明确时，摩擦来自界面还是机制”；每个主题说明涉及哪些议题和子议题、核心论点、证据、反例、设计含义和待验证的问题。
- **最后一节写 BUG**：分组列出，每组写现象、出现的场次和时刻，以及未整理的原话。
- 引用写法：
  - 实例：`[0924 i72](i:<session_id>/i72#TA-04.5)`。方括号里是短标签：场次 id 的月日（`20260924-…` 写 `0924`）加实例号；同一天有几场时，加开始时分区分，如 `0924·1531 i72`。`#` 后写这条证据在右栏所属的议题或子议题；不属于任何议题时省略 `#…`。
  - 议题：`[TA-04.5](issue:TA-04.5)`。
- **有理有据**：
  - 每个论断后面紧跟引用，一个论断引用 1–3 条最有代表性的证据，不堆砌；
  - 明说、画面或操作观察、你的推断要分开写，推断写成推断；
  - 记录者的原话加引号；数字（场次数、条数）以查询结果为准；
  - 不加原话和实例里没有的判断，不用泛化的 UX 术语替换记录者的说法。
- 可以用标题、段落、列表、加粗和简单表格。不要用图片或 HTML。

## 不做

- 不改写任何场次的 `experience-events.json`，不重新整理场次。
- 不新建、不改名、不合并洞察（顶层的 `TA-`、`N-`）；认为该合并、拆分或改名时，写进过程记录交给用户。
- 不改界面目录。界面名称的问题写进过程记录。
