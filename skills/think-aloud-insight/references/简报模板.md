# 分析简报模板

每份洞察报告开工前先写简报，交用户确认后再开工。简报决定报告从上往下怎么组织；用户的修改优先于模板。下面每一节都要填，填不出的写“待定”，不要替用户编。

实例：[示例_简报_手柄.md](示例_简报_手柄.md)（2026-10-21 手柄试点，用户确认过的简报）。

```markdown
# 分析简报：<主题>（<日期>）

## 给谁看
<读者是谁，读完要能回答什么。例：项目组各系统的 UX 设计师；读完要能回答“在我负责的系统里，玩家卡在哪、为什么卡、先修哪一处”。>

## 要回答的问题
1. <玩家在哪些系统、哪些环节，体验偏离了设计意图？>
2. <每一处偏离，在游戏里的原因是什么？哪些改同一条设计规则就能一起解决？>
3. <哪些最严重？>
4. <哪些地方是按意图运作的，不能改坏？>

## 设计意图
- **简报给出的意图**（来源：<用户 / 项目文档 / 记录者，注明来源类型>）：<一两句。写不出就留空，报告里标“意图待定”。>
- **已知的生产背景**（来源：记录者）：<例：界面先按键鼠设计，焦点逻辑后补。按事实写，不当推断。>
- **游戏内的原文**：提示、攻略、教学说明。agent 在证据和截图里找到的，原样引用，并注明场次和时刻。

## 分组
<默认按系统分组，也可以改成按体验阶段（首次 / 日常 / 长线）或按问题类型。跨系统的同一条规则，单独作为跨系统症结放在前面。>

## 来源类型
- A：记录者测自己设计的功能。懂设计意图，但对“玩家怎么理解”会因知识的诅咒失真；
- B：本项目里别人设计的功能。只共享项目通用规范，上手和理解类的发现较可信；
- C：其他游戏。接近中立的专业评测，不知道规范、技术背景和意图；“可能是有意设计”只能写成推测。

<本次材料属于哪类。记录者在原话里说“这是我做的”的证据，属于 A。>

## 严重度（单人评估）
从“低”起步，每有一问回答“是”上调一档：低 → 中 → 高 → 严重。
1. **核心体验**：这个问题下多数证据发生在主线、必经内容，或者经常要做的操作里吗？
2. **难以克服**：多数证据里，玩家在当前流程中自己解决不了吗？比如换设备、放弃或绕开、要离开去别处找答案、靠反复试错才过去、长时间卡住。“多做几步返工”不算。
3. **反复出现**：2 场及以上，或学过之后又犯？
“N 场”只说明同一个人反复遇到，不代表玩家普遍遇到。

## 本次不做
- 不写具体改法，只写机会点：“我们如何才能……”。
- 不写实现层面的免责说明。
- 报告的结构照常写回议题树（不加字段、不改资料库结构）；不新建、不改名洞察。
- <本次范围之外的主题。>
```
