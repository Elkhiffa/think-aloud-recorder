# 分析简报：手柄（试点，2026-10-21）

> 这份简报由用户确认后才开工。方法见同目录 `综合说明.md`。

## 给谁看

项目组的 UX 设计师，各自负责不同系统。读完要能回答：在我负责的系统里，手柄玩家卡在哪、为什么卡、先修哪一处。

## 要回答的问题

1. 手柄玩家在哪些系统、哪些环节，体验偏离了设计意图？
2. 每一处偏离，在游戏里的原因是什么？哪些是同一个原因，改一处就能一起解决？
3. 哪些最严重（按下面的三问）？
4. 哪些地方的手柄体验是按意图运作的，要保留、不能改坏？

## 设计意图

- **简报给出的意图**（来源：记录者，B 类，用户 10-21 确认）：
  - 手柄玩家不换设备，就能完成键鼠支持的全部操作；
  - A、B 键在各个界面的含义一致；
  - 在相同的界面里，按键的映射逻辑相同；
  - 焦点当前在哪里、走焦后下一步会到哪里，可以预测。
- **已知的生产背景**（来源：记录者，项目生产流程，用户 10-21 确认）：界面先按键鼠设计，同时兼顾移动端，焦点逻辑是后补的。这一点按事实写，不当作待证的推断。
- **游戏内的原文**：按键提示、设置里的手柄说明、教学提示。agent 在证据和截图里找到的，原样引用，并注明场次和时刻。
- 某个系统找不到可以对照的意图时，写“意图待定”，不要替设计方编。

## 分组

按系统分组。用证据所在界面的系统标签；战斗、HUD 和结算靠活动标签找到来源系统。跨系统的同一个原因，单独作为“跨系统症结”放在最前面。

## 来源类型

全部为 B：本项目、不是记录者设计的功能。

## 严重度（单人评估，标“单人评估（B）”）

从“低”起步，下面每有一问回答“是”，就上调一档：低 → 中 → 高 → 严重。

1. **核心体验**：是不是主线、必经玩法，或者经常要做的操作？
2. **难以克服**：在当前流程里自己解决不了，比如要离开去别处找答案（翻说明、问人、搜攻略）、靠反复试错才过去、长时间卡住，或者干脆放弃、绕开、换设备。
3. **反复出现**：在多场里反复遇到，或者学过之后又犯。

出现了几场只作为“反复出现”的证据，写成“N 场”，并注明它说明的是同一个人反复遇到，不代表玩家普遍遇到。

## 本次不做

- 不写具体改法，只写机会点：“我们如何才能……”。
- 不给议题表加字段；报告的结构照常写回议题树（2026-10-21 起的默认做法）。
- 只分析手柄。和手柄无关的问题，最多在附录里列一句。
