# 手动校准与事件表达（0.7.1）

`evidence` 返回 `manual_corrections.revision` 和按时间顺序的 `history`；每条含源结果 SHA、源素材 revision、事件 ID、修改前后字段、`changes` 与 unified `diff`。回看编辑只写 `experience-event-edits.json`，不改原结果、录像、逐字稿和证据。不要自行写这个文件。当前源结果匹配时，回看显示校准后的内容。

1. 首轮取材先读差异。相同源结果和事件多次修改，以最后一次值为准，之前的记录用于理解修正过程。不同源结果即使事件 ID 相同也不一定是同一事件；结合起止时间、内容和证据匹配，不能按 ID 生搬。素材已变更时重新定位。
2. 将修正整理成工作检查点，例如“明确说不理解红点时，要总结含义和定位困惑，而不是只写浏览界面”。人手校准表示用户真实意图和判断，但具体机制、按钮归属仍需证据；保留明确困惑，在 notes 限定未知因果。只在同场或相关情境验证有效，不自动修改全局 skill 或全库结果。
3. 新结果保留用户校准的事实、目标与感受，允许重分段、合并或补证。若新证据与校准冲突，说明具体冲突，不静默恢复旧表述。用户修正过的标题、时间、描述、问题和备注都需逐项核对。
4. 候选顶层添加 `corrections_review: {"revision":"本次读取的完整摘要", "summary":"逐项说明采纳、重新分段或有新证据而调整的内容，以及本轮采用的检查策略"}`。没有历史则可省略。提交前再次读取差异，有新修改就重核候选。摘要缺失或落后会拒绝提交；不要只更新摘要绕过核对。
5. 新结果发布前原结果被备份；校准历史永久保留供以后比较。新结果使用新的结果身份，不盲目叠加旧覆盖层。`corrections_review` 随新结果保存，作为此次采纳说明。原结果和手动修改均可追溯。

事件结构使用独立 `summary`（概述）、`issue`（问题与感受）、`notes`（备注／判断边界）。issue 和 notes 可空，最长分别3000和2000字。不要把所有问题藏进折叠证据，更不要用免责声明替代问题结论。

例如，原话“这个框是选中吗？”“红点在哪儿／干啥的？”支持“选中状态难辨认；红点位置和含义不清楚”的体验总结；“为什么做这么复杂？”支持理解或操作负担。它们不能单独证明焦点系统存在 bug。应将可支持的体验写入 issue，将“未复核对应画面，不能确认红点机制或实际键位冲突”放入 notes。引用保留源文字，不凭推测改写引用。

## 活动与问题的层级

事件单位是游戏内活动。先识别活动、参与目标和局部结果，再将不同问题与感受作为活动下的多个子项写入 issue（可分行）。问题可有轻重，程度由明确影响和原话支撑，不凭数量打严重度分数；问题多不等于事件多。

例如“货坊郎经营”作为一个事件，下面分别记选中状态、红点含义、上架操作和确认键位问题。它们不应成为四个事件；门派互动和独立多人建造也不应仅因时间相邻被塞进经营事件。先判断是否转入独立活动，不能为凑小事件把每次菜单切换切开。当前证据不足以确定边界时标明待校准范围，不猜准确切点。

提交前列出“活动 → 过程 → 问题子项”检查对应关系：活动标题不能只是一个问题句，也不能笼统列几个无关活动。反向检查每个已明确表达的问题是否保留在所属活动中；谨慎的因果判断放 notes，不让它吞掉体验事实。
